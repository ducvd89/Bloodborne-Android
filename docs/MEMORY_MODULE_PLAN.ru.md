# Модуль памяти прослойки: адреса видеочипа PS4 без sparse (план, 2026-10-09)

## Зачем

Новая модель памяти держит память игры в одной sparse-арене и переносит блоки между памятью
игры и VRAM перепривязкой (`vkQueueBindSparse`). На NVIDIA (Linux, драйверы ≥ 555) время
привязки растёт с числом уже привязанных страниц, вызов держит глобальную блокировку: каждый
перенос в VRAM стоил секунды, игра и рабочий стол вставали (GTX 1660 Ti, 615.71). Без переносов
(`BB_FIXED_ARENA=1`) — 48,6 FPS против ~205 на RX 7800 XT. Нужна модель, работающая одинаково на
AMD, NVIDIA и Intel, и не привязанная к буферному кэшу shadPS4: часть будущей прослойки запуска
игр PS4.

## Идея

У видеочипа PS4 своя виртуальная память (GPUVM) над общей памятью; любой V#, T#, указатель в
user data — виртуальный адрес. На ПК то же самое делаем средствами Vulkan 1.2 (BDA):

- **Источники памяти** — обычные (не sparse) буферы Vulkan:
  - куски памяти игры: dma-buf (AMD) или импорт памяти хоста (NVIDIA, Intel), по куску на
    выделение прямой памяти игры (выделения отображаются целиком — диапазон внутри одного
    отображения всегда непрерывен в одном куске);
  - зеркала в VRAM: сегменты, выровненные по адресам игры (страница игры X лежит в сегменте по
    тому же смещению), выделяются, когда в сегменте появляется первая страница в VRAM.
- **Таблица страниц** (буфер на видеочипе): страница адреса PS4 → адрес устройства (BDA) её
  текущего источника. Меняется копией в потоке команд — в порядке с отрисовками, без семафоров.
- **Прямой путь**: диапазон V# целиком в одном источнике (почти все привязки) → обычный
  дескриптор (буфер источника, смещение, размер). Транслятор шейдеров не меняется.
- **Страничный путь**: диапазон смешанный (≈85 огромных привязок за кадр: шейдеры, привязанные
  ко всей памяти) → дескриптор указывает на запись {адрес PS4, размер}, шейдер переводит каждый
  адрес через таблицу. Вариант пайплайна только для таких привязок (ключ специализации).
- **Вершины, индексы, аргументы indirect, копии, загрузка текстур**: прямой путь, иначе сборка
  в непрерывный временный буфер (только чтение) или копии по страницам (процессор знает таблицу).
- **Перенос в VRAM и обратно** — политика нынешней новой модели (данные, о записи которых мы
  знаем: загрузчики, видеочип; неизвестные писатели — на месте), но исполнение — копия + запись в
  таблицу + выбор источника при привязке. Привязки, записанные до переноса, читают старый
  источник — он ещё верен; освобождение VRAM — когда видеочип прошёл эти команды.

## Порядок работ

1. **Ядро модуля** (`gpu/layer/`, без зависимостей от shadPS4): источники, страницы, таблица,
   `Resolve(адрес, размер)` → прямой источник или «смешанный», обход по источникам для копий.
   Интерфейс записи команд — абстрактный (копия, запись таблицы), чтобы не тянуть планировщик.
2. **Подключение без VRAM**: новая модель отдаёт диапазоны на месте через буферы кусков, а не
   через арену; sparse-арена в новой модели не создаётся. Ожидание: ~48 FPS на AMD (как
   `BB_FIXED_ARENA`), никаких `vkQueueBindSparse`. Проверка картинки, затем сборка для NVIDIA.
3. **Зеркала в VRAM + перенос**: политика из `BufferCache`, таблица страниц, страничный путь в
   шейдерах для смешанных привязок. Цель — паритет с sparse-ареной на AMD (~205 FPS).
4. **NVIDIA/Intel**: тестовая сборка, лог тестера; затем убрать sparse из новой модели совсем.

Замеры — RX 7800 XT, стоя (`tools/bench.sh`), `BB_PC_MODEL=1`; диагностика `BB_RESIDENCY_MIX=1`.

## Состояние (2026-10-09, утро)

- Шаги 1–3 сделаны. На RX 7800 XT стоя: модуль ~205 FPS, sparse-арена ~205–238, старая модель
  ~220 (у лампы в Кошмаре охотника); в другом месте (1170 вызовов отрисовки) — 167,5 / 164,5 / 146.
  `vkQueueBindSparse` в режиме модуля не вызывается ни разу (счётчик в строке `Layer memory:`).
- Смешанные привязки решены без страничного пути: «летучие» блоки (`layer_volatile`) — блок с
  неизвестными байтами (край диапазона, промежуток между образами) кладётся в зеркало вместе с
  остальным диапазоном, обновляется из памяти игры перед каждой привязкой, а то, что запуск в него
  записал, копируется обратно после запуска (`LayerAfterBindings`). Страничный путь остаётся для
  привязок от 64 МиБ. `BB_LAYER_VOLATILE=0` — выключить (для сравнения).
- По умолчанию: AMD — sparse-арена, остальные видеокарты — модуль (`BB_LAYER_MEMORY=1/0` —
  вручную). Шаг 4 (NVIDIA): нужен лог тестера; путь импорта памяти хоста на AMD не проверить
  (RADV не импортирует memfd).

## Дополнение: оригинальное копирование и переносимые метки (2026-10-09)

В новом модуле исправлен paged-путь оригинального copy shader: записи обновляют память игры и актуальное зеркало; нативный шейдер теперь выбран по умолчанию. Для GPU-меток добавлен стандартный Vulkan-путь без AMD buffer marker. Реализация, переключатели и границы проверки описаны в [TRANSLATION_GPU_COPY_LABELS.ru.md](TRANSLATION_GPU_COPY_LABELS.ru.md). Это закрывает зависимость записи меток от AMD-расширения, но не заменяет аппаратную проверку NVIDIA.
