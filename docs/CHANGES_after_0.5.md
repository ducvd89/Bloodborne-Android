# Изменения после 0.5 (с 2026-10-10)

Замеры — RX 7800 XT / RADV, сохранение пользователя (Соборный округ), 1080p.

## Все розничные издания получают профиль игры (#119)

- Профиль Bloodborne (`gpu/games/bloodborne.cpp`) выбирался только для CUSA03173. Американское
  издание (CUSA00900) и остальные регионы запускают тот же исполняемый файл 1.09, но шли без
  профиля, и новая модель падала при входе в мир: `Guest fault ... at guest offset 0x2085xxx,
  address (nil)` в аллокаторе игры (#119, RX 7600, US-издание).
- Воспроизведено у себя на CUSA03173 с `BB_GAME_PROFILE=none`: то же падение (`0x208596a`) при
  входе в мир. С профилем, но без перехватов (`BB_GUEST_HOOKS=0`) — не падает: спасает
  `DynamicWriters` — код аллокатора, чьи служебные данные лежат в памяти GPU; без этой отметки
  их блоки уходят в VRAM-копию.
- Профиль, проверка игры (`scripts/game_check.py`), патчи (`scripts/patches.py`), «звуковой
  фикс» сохранений и папки модов теперь знают все издания: CUSA00900, CUSA00207, CUSA00208,
  CUSA00299, CUSA01363 и издания с The Old Hunters CUSA03179, CUSA03173, CUSA03014, CUSA03023.
- Проверка игры: другие регионы базовой игры без обновления просят 1.09 вместо «поддерживается
  только CUSA03173»; eboot.bin со вшитым патчем 60 FPS (падает в меню жестов) — отдельное
  сообщение (PR #117).
- Осталось: общий путь без профиля должен не падать сам (служебные данные аллокатора в
  VRAM-копии). Сейчас он нужен только для чужих игр.

## Размытие в движении на весь кадр в новой модели (#122)

- С включённым размытием в движении (по умолчанию) кадр при повороте камеры размазывался целиком,
  в старой модели — нет (#122, RX 9060 XT). Воспроизведено: резкость кадра во время поворота
  (стандартное отклонение лапласиана) 6,9 против 8,5–12 в старой модели.
- Поиск: `BB_GARLIC_VRAM_RANGE=начало,конец` (новый диагностический ключ: VRAM-копии только в
  этом диапазоне) и деление диапазона пополам — блок 64 КиБ `0x104ff00000`. Его читает только
  видеочип (буфер 11,4 МиБ каждый кадр), записей буферами и процессором нет: это память
  рендер-таргета, который игра потом читает как буфер.
- Причина: выгрузка изображения в память игры шла через staging и отложенную запись процессора,
  когда у этой памяти была VRAM-копия; копия обновлялась лишь после той записи (инвалидацией) —
  буфер читал данные прошлых кадров. Теперь видеочип копирует изображение и в арену (VRAM-копию)
  в порядке потока; в память игры — как раньше. И `IsRegionGpuModified` считает изменённым то,
  что видеочип записал в VRAM-копию (`gpu_written_bytes`, не на месте): без этого обновление после
  записи процессора поверх затирало копию старыми байтами (`BB_GPU_DATA_CHECK=0` — как раньше).
  Нужны обе правки. После: 11,9–13,0, как в старой модели; FPS тот же (127–131 в обоих
  вариантах, по три запуска).

## Нехватка VRAM на 4 ГБ больше не останавливает игру

- RTX 3050 4 ГБ, старая модель (Авто на NVIDIA), 0.5: три падения за вечер —
  `Failed to allocate 64 MiB for guest memory copies: ErrorOutOfDeviceMemory`. Запасного типа
  памяти (системной) для арены нет: разреженные буферы NVIDIA берут только VRAM. В pre5
  сборщик текстур стал держать текстуры по 5 с (FPS не падал со временем), и на 4 ГБ VRAM
  заканчивалась.
- Теперь: блок поменьше (ровно запрошенный), затем любой другой тип памяти, к которому можно
  привязать арену; и 30 с сборщик под давлением снова выселяет по отправкам, как до 0.5. Он же
  делает так сам, когда занято больше 92 % бюджета драйвера (`VK_EXT_memory_budget`, раз в
  секунду). Проверить можно только на такой карте.

## Выход из игры с геймпада (#74, #116)

- Оверлей (Insert или L3+R3): кнопка «Выйти из игры», второе нажатие подтверждает; игра
  закрывается как по кнопке окна.

## Мышь

- Камера мышью: щелчок в окне игры захватывает мышь (относительный режим SDL), F1 или уход из
  окна — отпускает; меню настроек и ввод имени тоже отпускают. Движение мыши — правый стик:
  отклонение по скорости мыши (~1000 пикселей/с — полный поворот при чувствительности 1), за
  60 мс спадает; движущаяся мышь сразу проходит мёртвую зону игры (`BB_MOUSE_DEADZONE`, 16 из
  127), так что медленное прицеливание тоже поворачивает камеру. Одинаково при любом FPS.
- Кнопки мыши и колесо — те же «клавиши» в привязках: `Mouse Left` R1, `Mouse Right` L2 (огнестрел),
  `Mouse Middle` R3 (захват цели), `Mouse X1` R2, `Mouse X2` L1, колесо — крестовина вверх/вниз
  (быстрые предметы); каждое деление колеса — короткое нажатие. Кнопки работают только при
  захваченной мыши: щелчок, который её захватывает, не атакует.
- bbport.ini: `mouse_look=0/1`, `mouse_sensitivity` (0.05–20), `mouse_invert_y`; лаунчер —
  *Управление*: «Камера мышью», чувствительность, инверсия; «Клавиатура и мышь» — назначение
  кнопок, «Назначить» принимает и кнопку мыши/колесо. Основа — PR #108 (виртуальный стик от
  движения мыши); раскладка клавиатуры не менялась.

## DLSS в AppImage и своя библиотека NVIDIA

- Сборка с `DLSS_SDK_ROOT` (DLSS SDK 310.9.1 с github.com/NVIDIA/DLSS) кладёт в пакет мост
  `libbbport_dlss.so`, `libnvidia-ngx-dlss.so.310.9.1` и `NVIDIA-DLSS-LICENSE.txt` (лицензия RTX
  SDK разрешает распространение в составе приложения, не отдельно). Тестовый AppImage:
  `dist/…-test-1010-dlss.AppImage`.
- Лаунчер, *Апскейлер → DLSS: библиотека NVIDIA → Выбрать файл…* — как DLL для FSR 4.1.1:
  `libnvidia-ngx-dlss.so.<версия>` копируется в `<user>/dlss/`, игра берёт её раньше встроенной
  (лог: `DLSS: NVIDIA's library from …`). Выбранная `nvngx_dlss.dll` — подсказка, что нужна
  библиотека для Linux. Мост ищется рядом с `bb-probe`, затем в `<user>/dlss/`.
- Мост собирается и с защитными флагами Nix (`-Werror=format-security`).
- Проверено на RX 7800 XT только до «not an NVIDIA GPU»: путь к библиотеке (встроенной и
  своей) выбирается верно. Сам DLSS — на карте NVIDIA RTX.

## Сборка из git после обновления с 0.4 (#124)

- `build.sh` останавливался: «patch failed: src/ffx_vk_fsr4_v07.c:35» — в подмодуле FSR-Vulkan

## Онлайн (shadNet) — отдельным модулем

- `gpu/bbnet` → `out/gpu/libbbnet.so`: сетевые и PSN-библиотеки shadPS4 из shadp2p (форк shadPS4,
  GPL-2.0) с клиентом shadNet, перенесены из Linux-форка bbport с онлайном (а тот — из Windows-порта).
  Модуль собирается отдельной целью, его C++ скрыт (`-fvisibility=hidden`, `-Bsymbolic`), наружу —
  только `bbnet_init` и `bbnet_resolve` (`gpu/bbnet/bbnet.h`). Свои заголовки модуля
  (`gpu/bbnet/include`) только дополняют общие: в `gpu/shim` и `gpu/shadps4` ничего не менялось.
- Рантайм (`src/runtime_net.c`): с `BB_ONLINE=1` на первом сетевом/PSN-импорте загружает модуль
  (`dlopen`, `RTLD_LOCAL`; `BB_NET_MODULE` — другой путь), отдаёт ему данные игры и гостевые потоки
  для обратных вызовов NP; трофеи, голос и диалоги магазина остаются в рантайме. Без `BB_ONLINE`
  модуль не загружается; без модуля или если он не стартовал — офлайн, как раньше.
- Сборка: protobuf, nlohmann_json, OpenSSL, zlib, miniupnpc (`shell.nix`); без них модуль не
  собирается (`BB_NET=OFF` — вручную), порт собирается как раньше. AppImage содержит модуль.
- `run.sh`: перенаправления адресов (`scripts/online.py`: сервер игры → The Hunter's Dream,
  знаки призыва → WebAPI shadNet), сервер shadNet по умолчанию `srv.shadps4.net:31313`.
- Лаунчер: страница *Онлайн* (сервер игры, сервер кооператива и WebAPI, учётная запись shadNet,
  UPnP, проверка соединения); `settings.json` — только для владельца (0600, там пароль).
- UPnP: порт P2P теперь открывается на роутере, когда транспорт готов, и закрывается при выходе
  (#121: `AddMapping` не вызывался нигде).
- Проверено: `tests/test_online.c` (импорты сети и NP → модуль, трофеи → рантайм); игра с
  `BB_ONLINE=1` без учётной записи доходит до уровня (модуль: 1399 функций; «no users connected
  to shadNet»). Вход в shadNet и призыв не проверены: нет учётной записи, а UDP-часть публичного
  сервера, по #121, не отвечает.
- HTTPS в AppImage: «Не удалось получить информацию от сервера Bloodborne» — проверка сертификата
  The Hunter's Dream проваливалась (`SSL server verification failed`): OpenSSL из Nix берёт корневые
  сертификаты из `/etc/ssl/certs/ca-certificates.crt`, а на NixOS это ссылка в `/nix/store` хоста,
  которого внутри AppImage не видно. Обёртки пакета теперь задают `SSL_CERT_FILE` на свой пакет
  сертификатов (`nss-cacert`), если указанный не читается; `run.sh` из исходников берёт системный.
  Лаунчер: текст ошибки в проверке соединения не терялся из-за разметки (`<urlopen error …>`), значки
  — из темы Adwaita.

## Мерцание главного меню при выводе выше 1080p

- С живой сменой разрешения (вывод 3840×2160 на мониторе 2560×1080) главное меню мерцало: часть
  кадров показывалась в родных 1920×1080 игры, остальные — с интерфейсом в разрешении вывода
  (4 из 50 снимков). `BB_UI_TRACE=1` (новая диагностика: отрисовки кадров без интерфейса в
  разрешении вывода) показал: пока меню анимирует подсветку, игра рисует его другими шейдерами
  Scaleform (`bb4d5f8c`, `e94b5b06`, `9951d199`, `44072322`, `a334a845`), а не `09957251`; их не было в
  списке шейдеров интерфейса (`ui_composition.h`), и такие кадры не собирались в разрешении
  вывода. После: 0 из 80; в уровне картинка та же.

## AppImage меньше

- В пакете были весь Mesa с LLVM (~800 МБ: нужны только Vulkan-драйверы RADV и ANV), полный GCC
  и заголовки Vulkan (их пути в отладочной информации `bb-probe`), 32-битная половина MangoHud
  (вторые glibc, gtk3, icu, perl) и GStreamer у GTK4 лаунчера. Теперь: свои RADV (без LLVM, ACO)
  и ANV без остального Mesa, `bb-probe` без отладочной информации, MangoHud 64-битный, GTK4 без
  GStreamer, печати и tracker.
- Ещё: SDL3 без зашитого zenity (тот тянул вторую GTK4 с GStreamer; теперь zenity хоста, если
  есть), libdecor без плагина GTK 3 (у SDL3 и у glfw MangoHud; рамки рисует его cairo-плагин),
  MangoHud без xdg-utils (Perl; `xdg-open` хоста). Сборка своей Mesa включает Dozen только потому,
  что рецепт nixpkgs ждёт его выход `spirv2dxil`; в пакет он не попадает.
- Итог: AppImage 925 → 399 МБ, пакет без сжатия 2,85 → 1,06 ГБ. Проверено: лаунчер открывается,
  игра из пакета стартует на встроенном RADV до титульного экрана.
