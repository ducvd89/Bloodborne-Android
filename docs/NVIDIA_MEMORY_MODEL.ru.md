# Новая модель памяти на NVIDIA: итог работы (2026-10-09)

Замеры ниже относятся к этапу разработки модуля. Актуальные изменения `0.5-pre2` и результаты
проверки оригинального copy shader: [CHANGES_0.5-pre2.md](CHANGES_0.5-pre2.md) и
[TRANSLATION_GPU_COPY_LABELS.ru.md](TRANSLATION_GPU_COPY_LABELS.ru.md).

## Задача

Новая модель памяти и трансляции (`BB_PC_MODEL=1`) держала память игры в одном sparse-буфере
(«арене») и переносила горячие блоки в VRAM перепривязкой страниц (`vkQueueBindSparse`). На
проприетарном драйвере NVIDIA для Linux это не работает: начиная с версии 555 время
`vkQueueBindSparse` растёт с числом уже привязанных страниц, а сам вызов держит глобальную
блокировку. У тестера (GTX 1660 Ti, драйвер 615.71) каждый перенос держал видеочип 10 секунд и
дольше, и вместе с игрой вставал рабочий стол. Поэтому новая модель была доступна только на AMD.

Цель: новая модель памяти на всех видеокартах.

## Решение: модуль памяти прослойки

Вместо sparse-арены работает собственный модуль памяти (`gpu/layer/bblayer_gpu_memory.*`,
`gpu/shadps4/video_core/buffer_cache/buffer_cache_layer.cpp`, план — `MEMORY_MODULE_PLAN.ru.md`):

- память игры привязывается **на месте**, через буферы её кусков (dma-buf на AMD, импорт памяти
  хоста `VK_EXT_external_memory_host` на NVIDIA);
- часто читаемое копируется в VRAM в отдельные буферы-«зеркала». Перенос сводится к копии и
  учёту в модуле, без перепривязки страниц;
- привязка берёт зеркало, если диапазон целиком в VRAM, иначе память игры на месте. Диапазоны от
  64 МиБ идут через таблицу страниц в транслированных шейдерах.

**`vkQueueBindSparse` в этом режиме не вызывается ни разу**: счётчик выводится в строке журнала
`Layer memory: ... vkQueueBindSparse: 0 calls`.

### Когда включается

| Видеокарта | По умолчанию |
|---|---|
| AMD | sparse-арена, как раньше |
| NVIDIA, Intel и остальные | модуль памяти, автоматически |

`BB_LAYER_MEMORY=1` / `=0` выбирает вручную. Лаунчер больше не прячет переключатель «Новая модель
памяти и трансляции» на видеокартах не от AMD. Стартовая проверка импорта памяти хоста в режиме
модуля проверяет запись видеочипа и процессора через сам импортированный буфер, без sparse-буфера.

## Что пришлось исправить, чтобы модуль заработал правильно и быстро

### Скорость: с 48–60 FPS до ~205 FPS на AMD (стоя у лампы)

1. **Подмена копий и очисток образов не срабатывала.** Детекторы `IsComputeImageCopy` и
   `IsComputeImageClear` ждали у шейдера ровно два буфера, а модуль добавлял каждому шейдеру
   третий — таблицу страниц. Копия целей рендеринга (`cs 3d5ebf4e`) и очистка (`cs 8b355b5a`,
   31 раз за кадр) выполнялись настоящими шейдерами через память, а образы 1080p
   перезагружались каждый кадр. Теперь таблица страниц не считается (`ShaderBufferCount`):
   60 → 136 FPS.
2. **Смешанные диапазоны.** Если у диапазона все блоки в VRAM, кроме одного-двух крайних с
   «неизвестными» байтами (промежуток между образами, чужие данные), весь диапазон читался через
   шину. Такие блоки теперь «летучие»: лежат в зеркале и обновляются из памяти игры перед каждой
   привязкой на чтение. 139 → 207 FPS. Для привязок на запись летучие блоки не используются.
3. **Перенос в VRAM при первой привязке** диапазона известных данных (как делала арена). Он
   соблюдает `BB_GARLIC_VRAM=0` и бюджет VRAM (`BB_VRAM_PROMOTE_PERCENT`, важно для карт на 6 ГБ).
4. **Нагрузка на процессор.** Ответы модуля кэшируются по поколению размещения; повторные
   проверки «можно ли перенести» — не чаще раза за кадр на диапазон; проверка «есть ли у
   диапазона копия в VRAM» — без блокировок, по счётчику версий модуля. Это сняло около 20%
   времени привязок и почти все блокировки в потоке командного процессора.

### Правильность: взрывы вершин и мусорные текстуры

Причина была одна: **копия в VRAM расходилась с памятью игры**. Найдено и закрыто несколько
путей:

1. **Код игры пишет в память без нашего ведома**: заголовки её кучи (`0x2085a60` / `0x20858a0`),
   часть загрузчика ресурсов (`0x216d420`). Блоки с копией в VRAM теперь защищены от записи
   собственными ловушками модуля. Запись проходит сразу, а блок возвращается на место перед
   следующей привязкой. Часто записываемые блоки остаются на месте навсегда (`NoteCpuWrite`).
2. **Чтения мимо модуля.** Мелкие привязки, кольцо констант и копирования командного процессора
   брали данные из памяти игры, хотя новые данные видеочипа лежали в VRAM: в новой модели
   `IsRegionGpuModified` знает только о незавершённых записях. Теперь всё, что задевает блок с
   копией в VRAM, идёт через модуль (`LayerMirrored`).
3. **Данные видеочипа затирали новые данные процессора.** При возврате блока на место и при
   повторной выдаче памяти игре модуль копировал «изменённое видеочипом» обратно, в том числе
   поверх того, что процессор успел записать позже: пометки ставились слишком широко. Теперь
   заявленные записи процессора снимают пометки со своих байтов (`LayerForgetGpuData`), выдача
   памяти заново снимает пометки со своего диапазона, а после незаявленной записи данные видеочипа
   в блоке считаются мёртвыми и назад не копируются.
4. **Куда видеочипу можно писать в VRAM** (`BB_LAYER_GPU_WRITES`): по умолчанию (`1`) — только в
   блоки, которые процессор не трогал с момента выделения: цели рендеринга и другие данные одного
   видеочипа. `0` — никогда (правильно, но 60–70 FPS: записи идут через шину), `2` — везде (давало
   взрывы).
5. **Шейдер копирования игры** в `0.5-pre2` по умолчанию транслируется в SPIR-V и выполняется
   на GPU. Таблица страниц содержит актуальное GPU-представление и адреса памяти игры;
   copy shader записывает результат в оба представления. Это устраняет расхождение зеркала
   VRAM и памяти игры без подмены оригинального списка копий на CPU.
   `BB_COPY_SHADER_NATIVE=0` оставляет HLE для сравнения.

На предыдущем этапе проверено в игре на AMD (модуль включён вручную, шейдер копирования через HLE): с
`BB_LAYER_GPU_WRITES=0` и с правилом «видеочип пишет в VRAM только внутри образов» — Сон
Охотника, собаки и трупы в Ярнаме чистые. На последней сборке (правило «блоки, которые процессор
не трогал») артефактов при игре не замечено, но отдельной проверки всех мест ещё не было.

## Замеры (RX 7800 XT, AMD, модуль включён вручную)

| Место | Модуль | Sparse-арена | Старая модель |
|---|---|---|---|
| У лампы, утром (до исправлений правильности) | ~205 FPS | ~205–238 | ~220 |
| Сон Охотника, сейчас | 130–144 FPS | — | — |

В Сне Охотника упираемся то в поток команд видеочипа на процессоре (~3,9 мкс на вызов при
~1500 вызовах за кадр), то в сам видеочип: проходы G-буфера 960×540, FSR ~1,07 мс.

**Открытый вопрос:** в части запусков на том же месте видеочип работает заметно медленнее
(70–95 FPS, FSR до 3,2 мс вместо 1,07). Причина не найдена; версии с компиляцией шейдеров,
поучастковым профилем `BB_SECTIONS` и обновлением летучих блоков не подтвердились. Сравнение
запусков осложняет то, что игра рисует разные проходы в зависимости от ракурса и сцены.

## Что не проверено

- **Сама NVIDIA.** На AMD путь NVIDIA (импорт памяти хоста + модуль) не воспроизвести: RADV не
  импортирует memfd. Нужен лог тестера.
- Карты с малым объёмом VRAM (6 ГБ): поведение при заполненной VRAM проверено только
  искусственно (`BB_VRAM_PROMOTE_PERCENT=1`: копий нет, ~38 FPS, стабильно).
- Intel.

## Что попросить у тестера на NVIDIA

Сборку с включённой в лаунчере «Новой моделью памяти и трансляции». В журнале должны быть строки:

- `Guest memory: host memory imported by the GPU (VK_EXT_external_memory_host ...)`;
- `Guest memory: the new memory model through the layer's memory module on this GPU (vendor 0x10de)`;
- `Layer memory: ... vkQueueBindSparse: 0 calls, 0 ranges; write traps hit N`;
- `Frame stats: ... FPS`.

Если видна строка `vkQueueBindSparse of N ranges took X ms`, значит, sparse где-то всё же
используется — это ошибка.

## Первые логи с NVIDIA и исправления (вечер 2026-10-09, `0.5-pre3`)

Тестер: GTX 1660 Ti (ноутбук, 6 ГБ, PCIe 3.0), драйвер 615.71, сборка 0.5-pre2. Импорт памяти
хоста и модуль включились, `vkQueueBindSparse: 0`.

1. **Зеркал не было вовсе** (10–15 FPS, мерцание фона на титульном экране): `FixedArena()` по
   умолчанию включалась при импорте памяти хоста и через `GarlicInVramForLayer()` запрещала модулю
   переносы. Теперь в режиме модуля она всегда выключена. До новой сборки обход — `BB_FIXED_ARENA=0`:
   с ним у тестера 30–35 FPS (видео), против 60–70 в старой модели.
2. **Кэш текстур и зеркала делили VRAM без общего бюджета.** Сборщик кэша текстур сравнивает с
   порогами всю VRAM процесса, зеркала тоже, а пороги на картах меньше ~9 ГБ — 40 и 80 %
   стартового бюджета (у тестера давление 1963 МиБ, критическая отметка 3927 МиБ). Переносы же
   вставали только на 90 % бюджета драйвера. Итог — 3,9–4,0 ГБ, сборщик постоянно за критической
   отметкой: 155–1255 выселенных образов за 5 с против 0–29 на AMD. Теперь:
   - переносы в VRAM встают за 384 МиБ до критической отметки (`VramPromotionsPaused`, строка
     `copies of loaded blocks wait`);
   - за 128 МиБ до неё модуль сам освобождает место (`LayerYieldToImages`): сначала обрезает запас
     роста зеркал, затем возвращает на место целые зеркала, не использовавшиеся 3 с
     (`BB_VRAM_PRESSURE_IDLE_SECONDS`).
3. **Перестройка зеркал.** Участок, примыкающий к зеркалу, создавал новое зеркало целиком с
   копией старого. При загрузке уровня это 15–27 ГБ выделений на 1,3 ГБ данных и всплеск VRAM до
   7,4 ГБ (у тестера в логе 5,6 ГБ при физических 6). Во время игры, при подгрузке районов,
   то же самое. Теперь растущее вверх зеркало получает запас под рост, равный своему размеру, но
   не больше 64 МиБ (`BB_LAYER_MIRROR_GROWTH_MB`): 5–10 ГБ выделений, худший кадр загрузки 555 →
   87 мс. Заменённые зеркала освобождаются на каждой отправке, а не раз в секунду.
4. **Записи `WRITE_DATA` в зеркало.** Командный процессор пишет на видеочипе в память игры; блок
   с зеркалом раньше уходил на место. Если диапазон целиком в одном зеркале, запись идёт в оба
   представления (`CommandWriteMirror`).
5. **Наблюдаемые блоки** (`BB_LAYER_WATCH`, по умолчанию включено). Блоки, в которых процессор
   когда-то писал без предупреждения, раньше всегда читались на месте, а значит на NVIDIA через
   шину. Теперь для читающих привязок они тоже получают зеркало под ловушкой записи. Запись
   процессора не возвращает блок на место: он перезаливается перед следующей привязкой, а
   ловушка взводится снова. Видеочип в такие блоки пишет на месте; блок, куда он записал,
   больше не наблюдается. Наблюдение почти полностью заменило летучие блоки (RX 7800 XT:
   1,3 ГБ/с перезаливок → 36 МБ/с; у тестера летучих было 455 МБ/с). Блоки, которые процессор
   пишет часто (3 кадра из 60), по-прежнему уходят на место: перезаливка их перед привязками
   завершала render pass (видеочип 4,8 → 7,2 мс за кадр). `BB_LAYER_WATCH_HOT=1` — эксперимент
   с ними.
6. Чтения файлов рантайма (`read`/`pread`) повторяются, если ядро вернуло `EFAULT`: ловушку могли
   взвести снова между касанием страниц и чтением.

Проверка на RX 7800 XT с `BB_VRAM_LIMIT_MB=5600` (пороги сборщика как у тестера: 1960/3920):
старая модель ~195 FPS; модуль ~200–213 FPS, видеочип 4,6–5,2 мс; VRAM держится ниже
критической отметки; маршрут `docs/route2.txt` без кадров дольше 25 мс; 3 минуты прогулки без
ошибок; картинка в Сне Охотника и в конце маршрута как без наблюдения. Сама NVIDIA этими
замерами не проверена: на AMD чтения на месте почти бесплатны.

## Отзывы на 0.5-pre3 и исправления (`0.5-pre4`)

- **GTX 1060 6 ГБ:** новая модель вровень со старой (41–48 FPS при ~1500 вызовах за кадр в обеих,
  видеочип 21–24 мс). Ранние просадки — компиляция шейдеров в первой сессии (160–241 компиляция
  за 5 с, рывки 1–3,7 с): теперь новые конвейеры проходов, рисуемых каждый кадр, собираются в
  фоне (`BB_ASYNC_PIPELINES`), а их отрисовки кадр-другой пропускаются.
- **Карта на 4 ГБ:** через ~4,5 минуты 5 FPS — регрессия pre3. Переносы в VRAM вставали за
  384 МиБ до критической отметки сборщика текстур (у карты 4 ГБ — нижние значения порогов,
  1536/3072 МиБ), а текстуры и служебные выделения уже держали 2808 МиБ: копий стало 124 МиБ на
  1,9 ГБ данных, видеочип ~200 мс на кадр. Теперь у зеркал своя доля (25 % бюджета драйвера,
  `BB_LAYER_MIRROR_FLOOR_PERCENT`): ниже неё пауза из-за сборщика не действует.
- **После телепорта ~10 FPS меньше:** большие привязки на всю память (через таблицу страниц)
  помечали каждые 2 МиБ как используемые, поэтому в игре ничего не простаивало, и зеркала
  покинутой локации держали VRAM. Теперь учитываются только прямые привязки
  (`layer_group_use`): при нехватке VRAM сначала уходят данные, к которым напрямую не
  привязывались 3 с, а зеркала с памятью без действительных блоков пересоздаются только поверх
  действительных (`LayerCompactMirrors`) — иначе частично вернувшееся на место зеркало держало
  всю свою память. На RX 7800 XT с `BB_VRAM_LIMIT_MB=4200–4600` это освобождало 160–490 МиБ за
  раз, картинка не менялась. На NVIDIA не проверено.

## Переключатели и диагностика

| Переменная | Что делает |
|---|---|
| `BB_LAYER_MEMORY=1/0` | модуль памяти вкл/выкл (по умолчанию: на не-AMD вкл) |
| `BB_LAYER_GPU_WRITES=0/1/2` | где видеочипу можно писать в VRAM (см. выше), по умолчанию 1 |
| `BB_LAYER_WRITE_TRAPS=0` | без ловушек записи (только для сравнения: вернутся взрывы) |
| `BB_LAYER_VOLATILE=1` | с летучими блоками (с 2026-10-10 выключены по умолчанию: их копии разрывали проходы рендера) |
| `BB_LAYER_PAGED=0` | без таблицы страниц для привязок от 64 МиБ |
| `BB_COPY_SHADER_NATIVE=0/1` | HLE / нативный шейдер копирования игры; в новой модели по умолчанию нативный |
| `BB_RESIDENCY_MIX=1/2` | привязки на месте / в VRAM / смешанные; `2` — ещё и самые тяжёлые с разбором блоков |
| `BB_LAYER_WRITE_LOG=1` | крупные записи видеочипа, оставленные на месте, и образы рядом |
| `BB_TOGGLE_FILE`, бит эксперимента 8 | чтение на месте вместо копий в VRAM (проверка устаревших копий) |
| `BB_TOGGLE_FILE`, бит эксперимента 16 | без обновлений летучих блоков |
| `BB_LAYER_WATCH=0` | без наблюдаемых блоков (блоки, где писал процессор, читаются на месте) |
| `BB_LAYER_WATCH_HOT=1` | наблюдать и часто записываемые процессором блоки (эксперимент) |
| `BB_LAYER_MIRROR_GROWTH_MB=N` | запас роста зеркала, по умолчанию 64; `0` — без запаса |
| `BB_VRAM_PRESSURE_IDLE_SECONDS=N` | при нехватке VRAM на место уходят данные, к которым напрямую не привязывались N с (3; `0` — нет) |
| `BB_LAYER_MIRROR_FLOOR_PERCENT=N` | доля бюджета VRAM, которую сборщик текстур не забирает у зеркал (25) |
| `BB_ASYNC_PIPELINES=0` | новые конвейеры компилируются сразу, игра ждёт (по умолчанию — в фоне для проходов, рисуемых каждый кадр) |
| `BB_ASYNC_PIPELINE_THREADS=N` | число потоков фоновой компиляции (по умолчанию четверть потоков процессора, 1–4) |
| `BB_VRAM_LIMIT_MB=N` | тест: бюджет VRAM драйвера считается не больше N МиБ (имитация карты на 6 ГБ: 5600) |
| `BB_RESIDENCY_MIX=1` | строка `Layer in place` теперь также говорит, почему блоки не наблюдаются |

## Что дальше

3. Летучие блоки обновляются на 0,9–1,6 ГБ/с — дешевле было бы обновлять их только после

4. Если модуль на NVIDIA подтвердится, перевести на него и AMD и убрать sparse-арену из новой
   модели.
